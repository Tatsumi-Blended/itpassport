1. なぜデータベースが必要か

製造現場のデータ管理における課題

製造現場でよくある「データの困りごと」

在庫管理の混乱

  • 部品表がExcelで管理されている
  • Aさんが編集中でBさんが開けない
  • 「在庫管理_最新版_田中修正.xlsx」が乱立
  • どれが正しいデータかわからない

品質データの分散

  • 検査データが各工程でバラバラに保存
  • ロット単位での追跡が困難
  • 不良発生時の原因究明に時間がかかる
  • データ間の整合性が取れない

Excel管理の限界を具体的に見る

シナリオ：部品在庫をExcelで管理している製造現場

Aさん
在庫登録中
→
ファイル
ロック状態
→
Bさん
「読取専用で開く」

同時編集

基本的に不可能。ファイルロックが発生

データ量

数万行を超えると動作が重くなる

入力ミス

「部品番号」に文字列も数値も入力可能

データベースが解決すること

Excel・CSVファイル

  • 1人ずつしか編集できない
  • データ量に限界がある（数万行程度）
  • 入力値の制約が弱い
  • ファイル間の整合性は手動で維持
  • 検索は遅い（全件走査）

データベース

  • 数百人が同時にアクセス可能
  • 数億件のデータも高速処理
  • データ型・制約で入力を厳格に管理
  • リレーションで自動的に整合性を保証
  • インデックスによる高速検索

製造業でのデータベース活用例

生産管理システム

  • 工程間でのリアルタイム情報共有

2. データベースの基本構造

RDBMS（関係データベース）の仕組み

RDBMS（関係データベース管理システム）

RDBMS = Relational Database Management System

データを「表（テーブル）」形式で管理し、表同士を「関係（リレーション）」で結びつけるシステム

商用製品

  • Oracle Database
    大企業の基幹システム向け
  • SQL Server
    Microsoft製、Windows環境に強い
  • DB2
    IBM製、メインフレーム系

オープンソース

  • MySQL / MariaDB
    Webシステムで広く利用
  • PostgreSQL
    高機能、地理情報対応
  • SQLite
    組み込み向け、ファイル単体で動作

テーブルの基本構造

部品マスタの例

部品コード 部品名 単価（円） 在庫数 発注点
P001ボルトM8×2515500100
P002ナットM88800200
P003平ワッシャーM831,200300
P004ベアリング62034505020

テーブル（表）

データを格納する「器」

レコード（行）

1件のデータ
例: P001の部品情報

フィールド（列）

データ項目
例: 部品名、単価

主キー（Primary Key）

主キー：各レコードを一意に識別するためのフィールド

「一意」= 1つに限定する、重複しない

主キーの条件

  • 一意性：重複した値は不可
  • NOT NULL：空値（NULL）は不可
  • 不変性：原則として変更しない

主キーの例

  • 部品コード（P001, P002...）
  • 社員番号（EMP001, EMP002...）
  • 受注番号（ORD-2024-00001...）
  • 自動採番ID（1, 2, 3...）

製造現場では「品番」「ロット番号」「設備コード」などが主キーになることが多い

複合主キー

単独で主キーになれる列がない場合、複数の列を組み合わせて主キーにする

受注No明細No商品コード数量
ORD-0011P001100
ORD-0012P00250
ORD-0021P001200

複合主キー：「受注No」+「明細No」の組み合わせ

→ 受注Noだけでは一意にならないが、明細Noと組み合わせると一意に識別できる

外部キー（Foreign Key）とリレーション

テーブル間を関連付ける仕組み

参照整合性：存在しない部品コードや倉庫コードは登録できない

→ データの矛盾を防ぎ、一貫性を保証する

データ型と制約

データベースが「入力ミス」を防ぐ仕組み

主なデータ型

データ型用途
INTEGER整数（数量、個数）
DECIMAL小数（金額、寸法）
VARCHAR可変長文字列（名称）
DATE日付（製造日、納期）

主な制約

制約意味
NOT NULL空値を禁止
UNIQUE重複値を禁止
CHECK値の範囲を制限
DEFAULT既定値を設定
FOREIGN KEY参照整合性

E-R図（Entity-Relationship図）

E-R図：データの関係性を「エンティティ」と「リレーションシップ」で表した設計図

用語説明例
エンティティ（実体） 人物、物など実世界の実体 学生、教員、部品、製品
リレーションシップ（関連） エンティティ間の関係 「担当する」「所属する」「構成する」

リレーションシップの種類

種類説明例
1対1 1つの実体に1つの実体が対応 校長と学校（1人の校長に1つの学校）
社員と社員証
1対多 1つの実体に複数の実体が対応 学校と学生（1つの学校に複数の学生）
部門と社員
多対多 複数の実体に複数の実体が対応 学生と受講科目（多くの学生が多くの科目を受講）
部品と製品

多対多の関係は、中間テーブルを使って2つの1対多に分解することが多い

3. データの正規化

効率的で矛盾のないデータ設計

正規化とは

正規化：データの重複を排除し、更新時の異常（不整合）を防ぐためのテーブル設計手法

重複の排除

同じ情報を複数箇所に持たない

更新異常の防止

1箇所を変更すれば全体に反映

データ整合性

矛盾したデータが入らない

正規化前の問題：受注データの例

問題のあるテーブル設計

受注No受注日顧客名顧客住所商品1数量1商品2数量2
0012024/01/15A製作所東京都大田区ボルトM8100ナットM8100

0032024/01/17B工業神奈川県横浜市ボルトM850ナットM850

冗長性

「A製作所」「東京都大田区」が重複して格納されている

更新異常

住所変更時、複数行を漏れなく修正する必要がある

構造の問題

商品3、商品4...と列が際限なく増える

正規化のメリット

  • 顧客情報は1箇所だけ（修正も1箇所）
  • 商品が増えても明細行が増えるだけ
  • 存在しない顧客や商品を参照できない

注意点

  • テーブルが分かれるので結合（JOIN）が必要
  • 過度な正規化はパフォーマンス低下の原因に
  • 実務では適度な非正規化も検討

正規化のレベル（参考）

第1正規形

繰り返し項目を排除
商品1, 商品2... → 明細テーブルへ

第2正規形

部分関数従属を排除
主キーの一部にだけ依存する項目を分離

第3正規形

推移的関数従属を排除
非キー項目間の依存関係を分離

ITパスポート試験では「正規化の目的」と「基本的な考え方」が問われる

データ操作の4つの基本

操作説明イメージ
選択 特定の行（レコード）を取り出す 「学生番号=2の学生を取得」
射影 特定の列（フィールド）を取り出す 「学生名だけを取得」
結合 複数の表を1つにまとめる 「学生と教員を教員番号で結合」
挿入/削除/更新 データの追加・削除・変更 「新しい学生を登録」

選択と射影のイメージ

【元のテーブル】
| 学生番号 | 学生名   | 電話番号         |
|---------|---------|-----------------|
| 1       | 山田太郎 | 090-9999-9999   |
| 2       | 鈴木愛子 | 080-8888-8888   |
| 3       | 上條恵   | 090-7777-7777   |

【選択】学生番号=2の行を取り出す（横方向）
| 学生番号 | 学生名   | 電話番号         |
| 2       | 鈴木愛子 | 080-8888-8888   |

【射影】学生名の列だけを取り出す（縦方向）
| 学生名   |
| 山田太郎 |
| 鈴木愛子 |
| 上條恵   |

選択 = 行（レコード）、射影 = 列（フィールド）と覚える

4. SQL入門

データベースを操作する言語

SQLとは

SQL（Structured Query Language）

データベースに対して問い合わせ（Query）や操作を行うための標準言語

読み方：エス・キュー・エル / シークェル

データ操作言語（DML）

操作SQL文意味
CreateINSERTデータ追加
ReadSELECTデータ取得
UpdateUPDATEデータ更新
DeleteDELETEデータ削除

その他のSQL分類

  • DDL：テーブル作成・変更
    (CREATE, ALTER, DROP)
  • DCL：権限管理
    (GRANT, REVOKE)

SELECT文の基本構文

SELECT 列名1, 列名2, ...
FROM テーブル名
WHERE 条件
ORDER BY 列名;

全件取得

SELECT * FROM 部品マスタ;

部品マスタの全レコード・全列を取得

特定の列を取得

SELECT 部品コード, 部品名
FROM 部品マスタ;

必要な列だけを指定して取得

WHERE句：条件による絞り込み

単一条件

SELECT * FROM 部品マスタ
WHERE 在庫数 < 100;

在庫数が100未満の部品を取得

複数条件（AND）

SELECT * FROM 部品マスタ
WHERE 在庫数 < 100
  AND 単価 > 100;

在庫少&高単価の部品（要発注）

演算子意味例
= / <>等しい / 等しくないWHERE 状態 = '有効'
> / < / >= / <=比較WHERE 単価 >= 100
BETWEEN範囲WHERE 在庫数 BETWEEN 10 AND 50
LIKE部分一致WHERE 部品名 LIKE '%ボルト%'
IN複数値のいずれかWHERE 倉庫CD IN ('W01', 'W02')

ORDER BY句：並び替え

昇順（ASC：小→大）

SELECT * FROM 部品マスタ
ORDER BY 在庫数 ASC;

在庫数の少ない順に表示
（ASCは省略可能）

降順（DESC：大→小）

SELECT * FROM 部品マスタ
ORDER BY 単価 DESC;

単価の高い順に表示

複合ソートの例

SELECT * FROM 部品マスタ
ORDER BY カテゴリ ASC, 在庫数 DESC;

カテゴリ順に並べ、同じカテゴリ内では在庫数の多い順

製造現場でよく使うSQLパターン

在庫不足部品の抽出

SELECT 部品コード, 部品名,
       在庫数, 発注点
FROM 部品マスタ
WHERE 在庫数 < 発注点
ORDER BY (発注点 - 在庫数) DESC;

特定期間の受注集計

SELECT 商品CD, SUM(数量) AS 合計数量
FROM 受注明細
WHERE 受注日 BETWEEN '2024-01-01'
                 AND '2024-01-31'
GROUP BY 商品CD;

実務ではBI（Business Intelligence）ツールがSQLを自動生成することも多い

テーブルの結合（JOIN）

複数テーブルを組み合わせてデータを取得

SELECT 部品マスタ.部品名,
       在庫テーブル.数量,
       倉庫マスタ.倉庫名
FROM 在庫テーブル
  JOIN 部品マスタ ON 在庫テーブル.部品コード = 部品マスタ.部品コード
  JOIN 倉庫マスタ ON 在庫テーブル.倉庫CD = 倉庫マスタ.倉庫CD
WHERE 在庫テーブル.数量 < 50;

正規化で分割したテーブルをJOINで結合し、必要な情報を横断的に取得

5. トランザクションとACID

データの信頼性を保証する仕組み

トランザクションとは

トランザクション：データベースに対する一連の処理をまとめた単位

「全て成功」か「全て取り消し」のどちらか

BEGIN
開始
→
処理1
処理2
処理3
→
COMMIT
確定

途中でエラー発生 → ROLLBACK（処理1から全て取り消し）

製造現場での例：出庫処理

トランザクション内の処理

  1. 在庫テーブルの数量を減らす
  2. 出庫履歴テーブルに記録を追加
  3. ロット追跡テーブルを更新

トランザクションの意義

処理2でエラーが発生した場合、処理1も取り消される

→「在庫は減ったが履歴がない」という不整合を防止

コミットとロールバック

用語説明タイミング
コミット（COMMIT） トランザクションが正常に完了した際に
更新内容を確定すること		 すべての処理が成功した時
ロールバック（ROLLBACK） トランザクションを取り消して
開始前の状態に戻すこと		 エラー発生時、処理中断時 
トランザクション開始 → 処理1 → 処理2 → 処理3 → コミット → 確定!
                              ↓ エラー発生
                         ロールバック → 処理1から全て取り消し

ACID特性

信頼性の高いトランザクション処理に必要な4つの特性

A：原子性（Atomicity）

トランザクション内の処理は「全て実行」か「全て取り消し」のどちらか

C：一貫性（Consistency）

トランザクション前後でデータの整合性が保たれる

I：独立性（Isolation）

複数のトランザクションが互いに干渉しない

D：永続性（Durability）

確定（COMMIT）したデータは障害後も失われない

ITパスポート試験では「ACID特性」の名称と概要が問われる

排他制御

排他制御：複数の人が同じデータを同時に更新しようとした場合に
矛盾が生じないようにする機能

→ データの一貫性を保つ

問題が発生するケース:

ユーザーA: 在庫数100を読み取り → 100-10=90 で更新しようとする
ユーザーB: 在庫数100を読み取り → 100-20=80 で更新しようとする
  ↓
同時に更新すると、最後に書いた方だけが反映される（10個分の出庫が消える）

ロック（Lock）

データベースへのデータの読み書きを一時的に制限する機能

1. ユーザーAがデータを読む前に【ロック】をかける
2. ユーザーBはロック中はデータにアクセスできない（待機）
3. ユーザーAが処理完了後、【アンロック】（ロック解除）
4. ユーザーBがデータにアクセス可能になる
ロックの種類説明
共有ロック 読み取り専用。複数ユーザーが同時に読める
排他ロック 更新用。他のユーザーは読み取りも更新もできない

DBMSとNoSQL

DBMS

Database Management System

アプリケーションの要求に応じてデータベースを操作するシステム

操作 → アプリ → DBMS → データベース

RDBMS vs NoSQL

種類特徴
RDBMS関係データベース
（MySQL、Oracle等）
NoSQLRDBMS以外
（MongoDB、Redis等）
