第1章

プロジェクトとは

独自の成果物を生み出す有期的な活動

プロジェクトの定義

期限内に独自のモノやサービスを作るための業務

プロジェクトの2つの特徴

1. 有期性

期限がある
開始と終了が明確

2. 独自性

成果が唯一無二
一度きりの活動

ITパスポートでは: 主に「システム開発」をプロジェクトの例として扱う

プロジェクトと定常業務の違い

項目プロジェクト定常業務
期間有限（終わりがある）継続的
内容一度きりの独自作業反復・ルーチン
目標成果物の完成業務の継続
組織一時的なチーム恒久的な部署
例システム導入、新製品開発経理処理、製造ライン稼働

プロジェクトの構成員

  ┌────────────────────────────────────────────┐
  │           プロジェクトオーナー              │
  │        （発起・提案する人、スポンサー）       │
  └────────────────────────────────────────────┘
                       ↓ 承認・支援
  ┌────────────────────────────────────────────┐
  │          プロジェクトマネージャ             │
  │       （プロジェクトを管理する人＝プロマネ）   │
  └────────────────────────────────────────────┘
                       ↓ 指示・調整
  ┌────────────────────────────────────────────┐
  │           プロジェクトメンバー              │
  │        （プロジェクトを遂行する人員）         │
  └────────────────────────────────────────────┘
プロジェクトマネージャの役割: 作業範囲、期限、費用を調整してプロジェクトを成功させる

第2章

3つの制約

トリプルコンストレイント

3つの制約とは

プロジェクトを制約する3つの要素

             スコープ
            （作業範囲）
                △
               / \
              /   \
             /     \
            /       \
           ◯─────────◯
      コスト           スケジュール
     （費用）            （期限）

1. スコープ

作業範囲
（何をするか）

2. スケジュール

期限
（いつまでに）

3. コスト

費用
（いくらで）

3つの制約の関係

三角形の3辺のような関係 - 相互に関わり合う

  【変更の影響】

  スコープを増やす → 期限延長 or コスト増加 が必要
  期限を短縮する → スコープ縮小 or コスト増加 が必要
  コストを削減する → スコープ縮小 or 期限延長 が必要

  ※ 1つを変更すると、他の1つまたは2つの変更が必要
  ※ 3つは独立していない、常にバランスを取る必要がある
試験ポイント: 選択肢に「リスク」が含まれることがあるが、3つの制約には含まれない

3つの制約の例

例: システム導入プロジェクト

状況対応策
追加機能の要望が発生
（スコープ増加）		 ・期限を延長する
・予算を増やす
・他の機能を削る
納期を2週間前倒し
（期限短縮）		 ・人員を増やす（コスト増）
・機能を減らす（スコープ縮小）
予算が10%削減
（コスト削減）		 ・機能を絞る
・期限を延長して人件費を分散

第4章

スコープマネジメント

WBS（作業分解構成図）

WBSとは

Work Breakdown Structure

  • プロジェクトの作業を階層的に分割したもの
  • Work（作業）をBreakdown（分割）
  • 「何をするか」を漏れなく洗い出す
プロジェクト
├── 大項目1
│   ├── 中項目1.1
│   │   ├── 作業1.1.1  ← ワークパッケージ
│   │   └── 作業1.1.2  ← ワークパッケージ
│   └── 中項目1.2
└── 大項目2
    └── ...

ワークパッケージ

WBSの最も小さい作業単位

8/80ルール

最小作業単位は8時間〜80時間（1日〜2週間）程度

  【良い分割の例】
  ○ 「仕様書作成」（20時間）
  ○ 「テスト実施」（40時間）

  【悪い分割の例】
  × 「コードを書く」（200時間）← 大きすぎる
  × 「コメント追加」（1時間）← 小さすぎる
100%ルール: 下位の作業を合計すると上位の100%になる

WBS作成の手順

1. ゴールを明確にする
   「何ができたら完了か？」

2. 大項目に分解する
   「主要な成果物・フェーズは？」

3. 中項目に分解する
   「それぞれ何が必要か？」

4. 作業に分解する
   「具体的に何をするか？」
   → ワークパッケージまで分解

加工機導入プロジェクト

横軸 = 時間（日、週、月）
縦軸 = 作業項目
バーの長さ = 作業期間

ガントチャートの要素

要素説明
タスク作業項目（縦軸）
期間バーの長さ（横軸）
開始日/終了日バーの位置
マイルストーン重要な節目（◆で表示）
依存関係前後関係を矢印で表示
予定/実績2本のバーで比較表示
ガントチャートの特徴: 進捗状況を視覚的に把握できる

アローダイアグラムとは

作業の流れを矢印で表した図

  【アローダイアグラムの記号】

  ●───────→●    矢印 = 作業（所要日数）
                  ○ = 結合点（ノード）

  ○ - - - →○    点線 = ダミー作業（所要日数0日）
                  作業の順序関係だけを表す
目的: 作業の順序関係や依存関係を表現し、最長経路を求める

クリティカルパス

プロジェクトで最も時間のかかる経路

      ┌─A(3日)─┐
開始─┤        ├─D(2日)─終了
      └─B(5日)─┘
          │
          └─C(4日)─┘

経路1: A→D = 3+2 = 5日
経路2: B→D = 5+2 = 7日
経路3: B→C = 5+4 = 9日 ← クリティカルパス

プロジェクト全体: 9日

クリティカルパス上の作業

余裕がゼロ
遅延 = 全体の遅延

それ以外の作業

余裕（フロート）あり
多少遅れても影響なし

クリティカルパスの計算問題

問題

      ┌─A(4日)─┬─C(3日)─┐
開始─┤        │        ├─終了
      └─B(6日)─┴─D(2日)─┘

各経路の所要日数を計算し、クリティカルパスを求めよ

解答

  • 経路1: A→C = 4+3 = 7日
  • 経路2: A→D = 4+2 = 6日
  • 経路3: B→C = 6+3 = 9日
  • 経路4: B→D = 6+2 = 8日

クリティカルパス: B→C = 9日

第6章

資源マネジメント

工数計算と効率

作業量（工数）の計算

新人とベテランでは作業効率が異なる

計算例

【条件】
・ベテラン: 1日で10件処理
・新人: 1日で5件処理（ベテランの半分の効率）

【問題】
100件の処理に必要な工数は？

【解答】
ベテラン2人×5日 = 100件 → 10人日
新人4人×5日×0.5 = 100件 → 10人日（実質20人日必要）
ポイント: 工数計算時は効率を考慮する

第7章

コミュニケーションマネジメント

伝達経路の計算

コミュニケーション管理の目的

誰が、誰に、いつ、どうやって、何を伝達するかを管理

コミュニケーションで大切なこと

  1. 情報の伝達遅れを防ぐ
  2. 知らせるべき人に送る
  3. 知らせてはいけない人に送らない

伝達経路の計算

メンバーが増えると伝達経路も増加する

計算式

伝達経路 = n × (n-1) / 2
メンバー数（n）伝達経路計算式
2人12×1/2=1
3人33×2/2=3
4人64×3/2=6
5人105×4/2=10
10人4510×9/2=45

組合せの計算（nCr）

n人からr人を選ぶ組合せの数

計算式

nCr = n! / (r! × (n-r)!)

計算例: 5人から2人を選ぶ（5C2）

5C2 = 5! / (2! × 3!)
    = (5×4×3×2×1) / ((2×1) × (3×2×1))
    = 120 / (2 × 6)
    = 120 / 12
    = 10通り

【簡単な計算方法】
5C2 = (5×4) / (2×1) = 20/2 = 10通り
伝達経路との関係: n人の伝達経路 = nC2 = n×(n-1)/2

第8章

リスクマネジメント

リスクの対処方法

リスクとは

将来起こりうる問題

リスクの評価

リスク発生確率影響度対策
設備納期遅延中高代替ベンダー確保
作業者の病欠中中複数人で担当
仕様変更高高変更管理プロセス
予算超過中高予備費確保

4つのリスク対応策

対応策説明例
リスク回避 リスクを発生させない
（スコープから外すなど）		 難しい機能は実装しない
リスク転嫁 他者にリスクを持ってもらう
（外部委託、保険）		 保険加入、外注化
リスク軽減 リスクを減らす
（発生確率・影響を下げる）		 多くのテスト実施
リスク受容 リスクをそのまま受け入れる
（何もしない）		 影響が小さいので対応しない

進捗管理

計画と実績の比較

進捗の測定

計画と実績の比較

作業A:
予定: ████████████░░░░ 75%
実績: ████████░░░░░░░░ 50%（25%遅れ）

作業B:
予定: ████████░░░░░░░░ 50%
実績: ██████████████░░ 87%（37%先行）

遅延への対策

対策内容トレードオフ
クラッシング 要員追加で短縮 コスト増加
ファストトラッキング 作業の並行実施
（本来は順番にやる作業を同時に）		 リスク増加、手戻り可能性
スコープ変更 範囲を縮小 成果物縮小
期限延長 スケジュール変更 ビジネスへの影響大

良い報告と悪い報告

悪い報告

「だいたい順調です」

  • 具体性がない
  • 問題を隠している可能性
  • 対策が立てられない
良い報告

「作業Aは予定の80%完了。電気工事が1日遅れているが、据付との並行作業で吸収予定。全体期限への影響なし」

  • 数字で具体的
  • 問題と対策を明示
  • 影響範囲も報告

プロジェクトマネジメントとの違いを理解する

プロジェクトとプロダクトの違い

プロジェクトマネジメント
  • 対象: プロジェクト（一時的な活動）
  • 目的: 期限内に成果物を完成
  • 期間: 有期（終わりがある）
  • 例: システム導入プロジェクト
プロダクトマネジメント
  • 対象: プロダクト（継続的な製品）
  • 目的: 製品価値の最大化
  • 期間: 継続的（終わりがない）
  • 例: スマホアプリの継続開発
ポイント: プロジェクトは「作って終わり」、プロダクトは「作った後も価値を高め続ける」

プロダクトマネジメントとは

製品やサービスの価値を最大化するための活動

ユーザー中心設計

  • ユーザーのニーズや課題を理解することが起点
  • 「作りたいもの」ではなく「ユーザーが求めるもの」を作る
  × 技術者視点: 「この技術を使いたい」
  ○ ユーザー視点: 「この課題を解決したい」

ペルソナとユーザーストーリー

ペルソナ

典型的なユーザー像を具体的に設定したもの

年齢、職業、行動パターン、課題などを詳細に記述

例: 「35歳、製造現場の班長、紙の報告書作成に時間を取られている」

ユーザーストーリー

ユーザーの視点で機能の目的を明確化

形式:
「○○として、△△したい。
なぜなら□□だから」
例: 「班長として、スマホで報告を入力したい。移動時間を有効活用したいから」

優先順位づけ

リソースには限りがある - 価値の高いものから着手

優先順位の判断基準

基準説明
ビジネス価値売上・利益への貢献度
ユーザー価値ユーザーの課題解決への貢献度
緊急度すぐに対応が必要か
実現可能性技術的・コスト的に実現できるか
依存関係他の機能との関係性

MoSCoW法

優先順位を4段階で分類する手法

分類意味説明
Must 必須 なければ成立しない機能
Should 重要 できれば実装したい機能
Could あれば良い 余裕があれば実装する機能
Won't 今回は実装しない 次回以降に検討する機能
覚え方: M-o-S-C-o-W の大文字を取って「モスクワ法」

MVP（Minimum Viable Product）

最小限の機能を持つ実用可能な製品

  • Minimum（最小限）
  • Viable（実用可能な）
  • Product（製品）

MVPの目的

  • 早期にユーザーからフィードバックを得る
  • 仮説を検証する
  • リスクを最小化しながら学習する

MVPの考え方

  【従来の考え方】
  × 機能をすべて作ってからリリース
    → 完成まで時間がかかる
    → ユーザーの反応が遅れてわかる
    → 修正が大規模になる

  【MVPの考え方】
  ○ 最小限の機能でリリース → フィードバック → 改善
    → 早くリリースできる
    → 早期にユーザーの声が聞ける
    → 小さく修正できる
例: 最初から100点を目指すのではなく、60点でリリースして改善を繰り返す

プロダクトバックログ

開発すべき機能や改善点を優先順位順に並べたリスト

バックログの管理

  • 常に優先順位を見直す
  • 新しい要望や課題を追加
  • 完了したものは削除

バックログアイテムの内容

  • 機能の説明
  • ユーザーストーリー
  • 受け入れ条件
  • 見積もり（工数）
イメージ: プロダクトの「やることリスト」を優先順位で管理

ロードマップ

プロダクトの将来計画を時系列で示したもの

  【ロードマップ例】

  Q1（1-3月）    Q2（4-6月）    Q3（7-9月）    Q4（10-12月）
  ────────────────────────────────────────────────────
  基本機能       レポート機能   分析機能       AI予測機能
  リリース       追加          追加          追加

ロードマップの活用

  • ステークホルダーとの共有
  • チームの方向性の統一
  • リソース計画の基礎
注意: 詳細すぎる計画は変更に弱い。柔軟性を持たせることが重要

KPIとメトリクス

プロダクトの成功を測定する指標

KPI（Key Performance Indicator）= 重要業績評価指標

メトリクス説明
アクティブユーザー数実際に使っているユーザー数
継続率（リテンション）継続して使い続ける割合
コンバージョン率目標行動を達成した割合
顧客満足度ユーザーの満足度
NPS他者への推奨意向（Net Promoter Score）
データに基づく意思決定: 主観ではなく客観的なデータで判断

プロダクトマネージャの役割

主な責任

  • プロダクトのビジョン策定
  • ユーザーニーズの理解
  • 優先順位の決定
  • ステークホルダーとの調整
  • 成果の測定と改善

関係者との連携

関係者連携内容
開発チーム要件の伝達、技術的制約の理解
デザイナーユーザー体験の設計
営業・マーケティング市場ニーズ、競合情報の共有
経営層ビジネス目標との整合
ユーザーフィードバックの収集

プロダクトマネジメント まとめ
