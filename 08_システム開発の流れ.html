1. システム開発の全体像

なぜ開発の流れを知る必要があるか

製造現場で起こること:

  • 「使いにくいシステムが導入された」
  • 「現場の意見が反映されていない」
  • 「何を伝えればいいかわからない」
開発の流れを知れば、適切なタイミングで意見を言える

システム開発の基本フェーズ

[企画] → [要件定義] → [設計] → [開発] → [テスト] → [運用]
  │         │           │        │         │         │
  │     ★最重要★      │        │         │         │
  │   ここで決まる      │        │    現場が      現場が
  │                     │        │    確認       使用
  │                     │        │
 何を作るか        どう作るか   作る

各フェーズの役割

2. 要件定義の重要性

要件定義とは

システムが「何をすべきか」を明確にするプロセス

現場の声: 「在庫がすぐ見たい」
            ↓
要件定義: 「在庫照会画面で、部品番号を入力すると
           3秒以内に現在在庫数と保管場所が表示される」

要件定義が不十分だと...

よくある失敗:

現場: 「すぐ見たい」
  ↓ 曖昧なまま開発
ベンダー: 「表示は1秒で出ます」（技術的な速度）
  ↓
現場: 「3回もクリックしないと見れない！」（操作が多い）
  ↓
「思っていたのと違う...」

機能要件と非機能要件

種類内容例
機能要件何ができるか在庫検索、発注登録
非機能要件どのように動くか応答3秒以内、稼働率99%

非機能要件の例

カテゴリ要件例
性能検索応答3秒以内、同時100人アクセス
可用性稼働率99.5%、障害時2時間以内復旧
セキュリティパスワード認証、操作ログ記録
使用性3クリック以内で主要機能にアクセス

要件の伝え方（悪い例）

「在庫管理を楽にしてほしい」

曖昧すぎて、何をどう改善すればよいかわからない

要件の伝え方（良い例）

「現在、部品番号を調べるのに平均5分かかっている。
部品番号を入力したら3秒以内に在庫数と棚番号が
表示されるようにしたい。対象は約5,000品目。
使用者は現場スタッフ30名。」

伝えるべきこと

  1. 現状の課題（定量的に）
  2. 期待する動作（具体的に）
  3. 対象データの規模
  4. 使用者の情報

3. 開発モデル

ウォーターフォールモデル

工程を順番に進める（後戻りしにくい）

[要件定義]
     ↓ 完了してから
[設計]
     ↓ 完了してから
[開発]
     ↓ 完了してから
[テスト]
     ↓ 完了してから
[運用]

ウォーターフォールの特徴

特徴:

  • 計画が立てやすい
  • 進捗管理しやすい
  • 要件変更に弱い

向いているケース:

  • 要件が明確で変わらない
  • 大規模システム
  • 品質重視

V字モデル

開発とテストを対応づけ

[要件定義] ─────────────────── [受入テスト]
     ↓                              ↑
  [基本設計] ─────────────── [結合テスト]
       ↓                        ↑
    [詳細設計] ──────── [単体テスト]
         ↓                  ↑
        [開発] ─────────────┘

V字モデルのテスト対応

工程テスト確認内容
要件定義受入テスト要件を満たすか
基本設計結合テスト機能間の連携
詳細設計単体テスト個々の機能

アジャイル開発

短いサイクルで開発・フィードバックを繰り返す

┌────────────────────────────┐
│ スプリント1（2週間）       │
│ [計画]→[開発]→[レビュー]  │
└────────────┬───────────────┘
             ↓ フィードバック反映
┌────────────────────────────┐
│ スプリント2（2週間）       │
│ [計画]→[開発]→[レビュー]  │
└────────────┬───────────────┘
             ↓ 繰り返し

アジャイルの特徴

特徴:

  • 変更に柔軟
  • 早期にフィードバック
  • 密なコミュニケーション必要

向いているケース:

  • 要件が変わりやすい
  • 小〜中規模
  • スピード重視

開発モデルの比較

項目ウォーターフォールアジャイル
計画性高い低い
柔軟性低い高い
成果物の早さ遅い早い
文書量多い少ない
向いている規模大規模小〜中規模

4. テストの種類

テストの段階

テスト実施者内容
単体テスト開発者個々の機能を確認
結合テスト開発者機能間の連携を確認
システムテスト開発者全体の動作を確認
受入テスト発注者要件を満たすか確認

受入テストの重要性

現場がチェックすべきこと:

  • 要件通りの機能があるか
  • 操作が想定通りか
  • エラー時の動作は適切か
  • 性能は問題ないか（応答速度など）
  • 実際のデータで問題ないか

テストケースの例

No操作期待結果OK/NG
1存在する部品番号で検索在庫数が表示される
2存在しない部品番号で検索エラーメッセージが表示される
3在庫0の部品番号で検索0と表示される
